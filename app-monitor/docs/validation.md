# 验证记录

验证日期：2026-10-18，时区：Asia/Shanghai。

## 1. App 与网页接口关系

网页版现有实现监听：

```text
h5api.m.goofish.com/h5/mtop.taobao.idlemtopsearch.pc.search
```

Mac 版闲鱼 7.28.60 使用原生 MTOP 搜索接口：

```text
https://acs.m.goofish.com/gw/mtop.taobao.idlemtopsearch.search/1.0
mtop.taobao.idlemtopsearch.main.item.search
```

两端属于同一搜索业务体系，但网关、签名、设备上下文和风控入口不同，不能直接互换请求。

## 2. 未登录验证

未登录状态切换“新发”后，正式 App 发出的请求包含：

```text
sortField=create
sortValue=desc
gmtCreate:desc
user_id=0
```

页面仍显示登录引导，首屏商品显示约 6 小时和 8 小时前发布。没有发现客户端请求中存在“过滤最近 6 小时”的开关，因此该窗口来自服务端匿名结果裁剪。

结论：修改 UI、隐藏登录提示或复现匿名请求都不能获得被隐藏的新商品。

登录 Mac 版闲鱼后，通过深链打开 `trackpad`，再点击“新发”。

20:17 观察到的两个首屏曝光事件分别为：

| 列表位置 | 价格 | 精确发布时间 | 页面状态 |
| --- | ---: | --- | --- |
| 0 | 218.02 | 20:10:11 | 刚刚发布 |
| 1 | 640 | 20:09:03 | 刚刚发布 |

本次请求仍确认 `sortField=create`、`sortValue=desc`。结果发布时间距观察时间约 7 至 9 分钟，说明登录后匿名约 6 小时的限制已经解除。

页面同时出现“为您挑选以下和搜索词更相关的商品”，其中一条是 iPad Air，说明“新发”结果仍可能混入相关召回，标题过滤不可省略。

## 4. 可访问性验证

登录后的搜索结果页可访问性树直接包含：

- 完整商品标题；
- 价格，例如 `640元`；
- 展示地区，例如 `上海`；
- 标签，例如 `发货极快`；

因此标题读取不需要 OCR。此前“只能 OCR”的判断不成立，问题来自当时页面状态和操作链路不稳定。

## 5. 本地数据库验证

搜索后发生变化的数据库包括：

```text
~/Library/Containers/com.taobao.fleamarket/Data/Library/walle_ut_user_track.db
~/Library/Containers/com.taobao.fleamarket/Data/Library/edge_compute.db
```

`walle_ut_user_track.db` 中新增的 `Page_xySearchResult_Appear-Item` 事件可解析出商品 ID、关键词、价格、发布时间和列表索引。当前页面上两个“刚刚发布”商品均能在事件中找到对应记录。

标准 URL 缓存只保存 `search.shade` 配置，没有保存完整商品搜索响应。

## 9. 首页地区搜索与排序点击

2026-10-19 在首页底部第二个 Tab 为「厦门」时验证：点击该 Tab，从首页搜索框输入 `iPhone 17` 并点击搜索，结果页排序栏直接显示「厦门」，无需再打开「区域」面板。

2026-10-20 运行 56 的首页地区搜索未提交：点击搜索框后，实际焦点控件为 `AXTextArea`，输入校验只接受 `AXTextField` / `AXComboBox`，于是回退到深链。深链打开的结果页排序栏显示「区域」，不会继承首页「厦门」Tab。应接受位于顶部搜索框内的可编辑 `AXTextArea`，写入后回读验证，再提交搜索；地区跳过仍以结果页城市文字为准。

后续实测发现该 `AXTextArea` 的焦点位置在搜索框内，`AXValue` 报告可写且写入返回成功，但回读仍为空，页面关键词也没变化。`CGEvent.postToPid` 定向发送按键时没有抢占焦点，也没有改变关键词。后台运行时需回退深链并在结果页执行地区筛选；闲鱼本身已在前台时，才使用真实键盘输入并回读核对。

后台回退链路实测：深链搜索 `iPhone 17` 后排序栏为「区域」，通过结果页排序栏中的「区域 > 福建 > 厦门 > 查看」可完成筛选，随后排序栏显示「厦门」。对地区入口增加排序栏定位，并在筛选后再次读取城市标签，避免把仅仅点击成功记作地区已生效。

2026-10-20 容量筛选复核：筛选弹层中 `256GB` 文字节点的 `AXPress` 虽返回成功，画面没有出现选中勾号；随后按「确定」只会提交空筛选。对同一弹层内的容量格发送前台坐标点击后，画面出现勾号，按「确定」后结果页容量标签显示 `256GB`。容量格支持多选；从 256GB 切到 512GB 必须取消前者、选中后者并再次按「确定」。采集端应以提交后结果页容量标签为成功依据，不再以 AXPress 返回值判断筛选成功。

2026-10-20 判价口径修正：用户确认每日报价是回收报价，允许商品挂牌价在报价之上保留议价空间。例如报价 ¥4900、允许高于报价 ¥200 时，挂牌价 ≤ ¥5100 均进入推送候选；旧实现的「报价减最低价差」导致上限误算为 ¥4600。页面和通知应显示与回收报价的相对差额，不把尚未议价的金额称为“省”或利润。

此前“新发 / 降价找不到元素”由两个问题共同造成：结果页只固定等待 3 秒，排序栏尚未出现；点击器还会优先对大范围父容器执行 `AXPress`，可能误点其他内容。调整为等待排序栏实际出现，并按“元素自身动作 → 文字中心坐标 → 父元素动作”点击后，真实 App 中连续点击「新发」「降价」均成功。

端到端只读采集验证结果：地区已应用，`新发` 读取 10 张卡片和 1 条本轮曝光并关联出 1 件商品；`降价` 读取 8 张卡片和 1 条曝光，按钮点击无错误。本轮未执行价格匹配和外部推送。

## 11. 后台操作原理实测

2026-10-19 在闲鱼处于后台、Codex 保持前台时，对无副作用的底部「我的」Tab 做了对照：

- 将鼠标 `CGEvent` 定向投递到闲鱼 PID（`postToPid`）后，进程报告事件已投递，前台应用和鼠标坐标均未改变；但 Accessibility 树没有切换到个人页标志，说明“投递成功”不等于 App 执行了点击。
- 对同一按钮调用 macOS Accessibility `AXPress` 后，个人页标志出现在 Accessibility 树中；Codex 仍在前台，鼠标坐标也未变化。随后用 `AXPress` 切回「首页」。

结论：当前 Mac 版闲鱼可在后台通过语义化 Accessibility 动作切换页面；本次没有证明按 PID 投递的 Quartz 鼠标事件能驱动该 App。接下来优先把采集链路中剩余的鼠标滚轮 / 坐标动作替换或验证为 Accessibility 原生动作；若控件不暴露可执行动作，则将其作为需要前台 UI 自动化的边界单独处理。该验证只覆盖 Tab 切换，未覆盖搜索、滚动和商品卡片点击。

## 12. 曝光事件的链接与图片字段

2026-10-19 对本机曝光库只读检查最近 300 条搜索商品曝光事件：解析到 31 条商品曝光、28 个不同商品 ID。事件字段中未发现原始商品 URL 或图片 URL；`picWidth` / `picHeight` 只是尺寸字段，不包含图片地址。

当前采集器根据曝光里的真实商品 ID 生成 `https://www.goofish.com/item?id={item_id}`，因此可得到可点击的候选链接，但它不是曝光事件直接提供的 URL，也尚未在本轮验证链接可访问性。现有图片 URL 提取逻辑在这些记录上命中 0 条，不能据此给商品推送配图。标题、价格、地区等仍由曝光 ID 与 Accessibility 可见卡片关联取得；图片若是必需项，需要另行验证 App 的 Accessibility 图像属性或其它只读本地数据源。

同日按用户要求通过已配置 Webhook 推送一条最新曝光商品用于链路检查，服务端返回 HTTP 200；用户随后反馈未收到推送。该条使用由商品 ID 生成的链接且没有图片地址；HTTP 200 只证明 Webhook 接收成功，不证明目标渠道已送达、手机端已展示或图片显示正常。用户确认生成的商品链接可打开。

## 13. 容量筛选误点击与控制台日志

2026-10-19 根据运行记录和闲鱼当前界面复测：点开「筛选」后，第一层显示「存储容量」分类；点入后才出现容量项和「确定」。搜索结果商品卡片本身也包含 `256GB` 等文字，旧路径 `筛选 > 256G > 确定` 会把卡片容量误当筛选项并打开商品详情。

修正默认路径为 `筛选 > 存储容量 > {容量} > 确定`。A11y 容量选择现在必须定位到「存储容量」标题与确认按钮之间的选项；未找到该筛选上下文时拒绝点击页面其它同名容量文字。对当前 App 的实测中，`256G > 确定` 两步均由 AXPress 完成，筛选后排序栏仍存在；随后「新发」「降价」均成功点击，页面仍保持搜索结果状态。

采集、筛选失败/恢复、排序结果与商品摘要已加入 INFO/WARNING 控制台日志。需要重启 `app-monitor` 才会加载新代码；本次没有替用户重启服务。
